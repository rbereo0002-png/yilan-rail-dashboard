# 宜蘭高架：由 AI 協助登錄的中央主檔／唯讀發布作業規範
版本：115/11/18（測試分支規範，非正式核定作業程序）

## 一、已確認的運作方式
1. **中央資料庫為維護主檔**：Supabase `yilan-rail-control-test` 的 `public.rail_control_snapshots` 保存 north/south 各一份完整現行資料，`rail_private.shared_control_topics` 保存跨標段共管主題，`rail_private.shared_control_links` 保存各標段原始 ID 的關聯。版次歷史由 `public.rail_control_change_history` 觸發器保存。
2. **前端只讀**：承辦人版與長官版皆從同一組已審核發布的 `data/north.json`、`data/south.json` 計算呈現；使用者無需資料庫帳號，頁面不得提供資料庫寫入或本機履約資料保存。
3. **兩種「同一份」要分清**：中央資料庫是真正寫入主檔；GitHub 的 JSON 是核對後才同步的唯讀**發布副本**，不是另一個可任意編輯的業務主檔。資料庫更新後，GitHub 在發布完成以前可能暫時較舊；絕不可聲稱此期間已即時同步。
4. **權限安全**：原有公用 GitHub Pages 並不等於內部機密網站。GitHub JSON 若在公開 repo，即可供外界閱讀。因此新資料入庫不等於可以全文公開。核對是否含個資、機敏議價、未核定決策、未公開公文後，再決定可否發布。
5. **取消前端帳號**不代表移除中央資料庫的 RLS 保護。匿名者不可直接透過 Supabase 讀取維護主檔；AI 每次受委託時，透過已連線的資料庫及 GitHub 操作工具記錄，不儲存專案檔至瀏覽器本機。

## 二、每次收到來函、會議紀錄或審查成果的登錄順序
1. 先直接讀取該次上傳來源及參照契約/附件A/核定紀錄。比對日期、文號、主辦/協辦單位、北/南/全案範圍與契約期限依據。來源不可查實者，不得以猜測補入。
2. 先列出有待確認的矛盾（如「函稿」與「正式發文」、「簡報提送」與「方案核定」、「已完成會議」與「已解除列管」）；在資料狀態保留未確認，而非逕行結案。
3. 讀取資料庫當前 `project_key`、`revision`、`document`；同一事項以穩定 ID 更新。新紀錄需來源文號、事件日、收文日、核定狀態、證據。
4. 審查成果：首次提送日期及契約原期限不動；目前版本 A→B 時先將 A 版送審、審查／退回、文號寫入 `versionTracking[id].history[]`，新版本 `currentVersion` 與 `currentDue` 另存。若僅有函稿，`returnEvidenceStatus='draft'`、`deadlineConfirmed=false`，不得算正式退回逾期。正式核定或通知來函後再標明確認。
5. 跨段共管：先查 `rail_private.shared_control_topics` 是否已有同題，並沿用全案 `topic_key`；各標段可各自有 `legacy_control_id`、負責單位、日期、證據及子任務。**不因名稱相近就刪除標段原始紀錄。**
6. 比對資料庫版本號後以受控 UPDATE 將 `revision` 精確加 1，舊版由觸發器自動存入歷史。若 revision 不符，不得覆寫，須重新讀取與合併。
7. 入庫後立即查核：資料庫 revision、差異、歷史備份、南北段事件數、KPI 分類、同月臺北段限定、契約/管理期限分類；不以 GitHub 的舊資料覆蓋較新的 DB。
8. 發布前先製成**已審核、可公開**的同版 JSON；更新到 GitHub 測試分支，跑完自動測試並核對長官/承辦兩種呈現及統計，通過後才依發布授權更新正式分支。每次發布記錄來源 DB revision 與 Git commit。若任一步驟失敗，保留資料庫入庫紀錄但標示「尚未發布」，不可回報網頁同步成功。
9. 回復使用者「已登錄／尚待核對／已發布」三種不同結果，標明變更標段、控制 ID、版次、來源、驗證及尚待事項。

## 三、審查版次目前顯示原則
- 每一成果只有一個現行審查主項，A 版退回後主畫面顯示「待提 B 版」、退回日期及 B 版期限。
- 已提 B 版顯示「B 版審查中」，不把 B 版初次提送期限繼續列為逾期未提。
- 已完成 A 版之期限供歷史查詢、原契約是否如期統計，不在主時程再次列管。
- 草稿函日期、暫定管理日、PCM 契約審查期限與甲方核定日必須分欄呈現。
- 「送審已完成」不等同「審查通過」，「會議已召開」不等於「交辦事項完成」。
- 工作計畫審查核定管理預估 1 個月；基本／細部設計審查核定管理預估 2 個月，應與 PCM 契約期限分開。

## 四、現況與發布門檻
- 資料庫已匯入 north/south，各 revision = 1；10 個共管主題各有北、南兩個原始 ID 關聯（共 20 條）。
- 目前網站程式仍在獨立 PR #15；正式 main 無變更。
- 目前測試分支在不使用帳號的前提下讀取 GitHub JSON 唯讀發布副本，**不是從瀏覽器直接連線 Supabase**。後續由 AI 逐次完成資料庫登錄及已審核發布的同步。
- GitHub Actions 的契約/審查及舊版 RC 回歸皆須通過；不可單憑資料庫已有紀錄認定已正式上線。
- 手機／平板、實際頁面、公開資訊審查及兩種看板統計比對都必須核實後才准切換正式版。
